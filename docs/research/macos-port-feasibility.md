# macOS port: feasibility and what it takes

Researched 2026-11-23. This note extends [clipboard-history-platform-apis.md](clipboard-history-platform-apis.md) (called **R** below); it does not repeat what R already covers in sections 1.3, 2, 3, 4, 6 and 7. It adds three things: a gap analysis against *this* codebase, the macOS changes since R (2026-11-12), and the answers to the macOS items in R's open questions.

Sources: Apple developer documentation (read through its JSON API at `developer.apple.com/tutorials/data/documentation/…`, same text as the rendered pages linked below), Apple release notes, Apple Developer Forums posts by Apple staff, nspasteboard.org, Tauri's docs, and the source of crates already in `src-tauri/Cargo.lock` (read from the local cargo registry: `tauri 2.12.4`, `tao 0.37.1`, `tauri-plugin-autostart 2.7.0`, `auto-launch 0.6.0`, `global-hotkey 0.8.0`, `objc2-app-kit 0.3.2`, `objc2-core-graphics 0.3.2`, `objc2-foundation 0.3.2`). Maccy (an open-source, shipping macOS clipboard manager) is cited as a working example, not as an authority. Markers: **(inference)** is my conclusion; **(unverified)** means I found no primary source.

---

## Verdict

**Yes, with caveats.** Every Backend capability the Linux side has (watch, read every Format, write, Echo, secret skip, source app, auto-paste, global shortcut, tray, autostart, update) has a macOS mechanism, and the needed APIs are reachable from **safe** Rust through `objc2-app-kit` / `objc2-core-graphics`, which are already in the dependency tree. That matters because `Cargo.toml` has `unsafe_code = "forbid"`. The core (`core/`, `store/`, `engine`) needs no changes beyond one optional Capabilities field.

The caveats are all about permissions and distribution, not code:

1. **Pasteboard privacy (macOS 15.4+).** Programmatic reads of the general pasteboard ask the user by default. A clipboard manager reads on every change, so the user must pick "Always Allow" once. Whether that alert is enforced by default on current macOS (27.x) is still **(unverified)** (section 3).
2. **Auto-paste needs the Accessibility permission**, and **macOS 27.3 (beta 2, current as of this date) is reworking that permission pane**, with entitlements for "new installations" whose details Apple has not published yet (section 4). This is the biggest unknown.
3. **Distribution practically requires the paid Apple Developer Program ($99/yr), Developer ID signing and notarization.** Without a stable signature, every update silently loses the Accessibility grant. Since macOS 15, unsigned apps can no longer be opened with Control-click (section 7).
4. **The popup's focus model differs.** Tauri windows are `NSWindow`s, not non-activating `NSPanel`s, so the popup has to activate our app and then hand focus back to the previous app before pasting. The existing `FocusTracker` trait fits that (section 5).

Rough size: one macOS Backend module of about the same size as `x11.rs` + `x11_paste.rs`, but simpler (polling instead of selection-protocol I/O, no INCR), plus a signing/notarization pipeline **(inference)**.

## 1. What the Linux side assumes (gap analysis)

Each row is a Linux-specific assumption in the current code and what macOS needs in its place.

| Where | Linux assumption | macOS counterpart |
|---|---|---|
| `lib.rs` `make_backend` / `make_paste` | `#[cfg(not(target_os = "linux"))]` returns `Err("This platform is not supported yet")` / `None` | `#[cfg(target_os = "macos")]` versions that build a `MacBackend`, `MacPaster` and `MacFocus` from `platform/macos/` |
| `platform/linux/mod.rs` `choose` | picks X11 / XWayland / Unsupported from `XDG_*`, `DISPLAY` | no choice to make: one Backend. Nothing like `choose` is needed |
| `x11.rs` watcher | event-driven (XFixes `SelectionNotify`); one thread owns the X connection and also *serves* our writes | polling `changeCount` on a thread; the pasteboard server stores our data, so there is nothing to serve (section 2) |
| `x11.rs:248` own-write skip | `e.owner == s.win`: our own window owns CLIPBOARD, so no ClipEvent | compare `changeCount` with the value `clearContents()` returned for our write (section 2.4) |
| `x11.rs:310` secret skip | `x-kde-passwordManagerHint == "secret"` sets `ClipEvent.secret` | `org.nspasteboard.ConcealedType` / `TransientType` / `AutoGeneratedType` and legacy markers (section 6, **required**) |
| `x11.rs` `source_app_of` | `_NET_WM_PID` then `/proc/<pid>/comm` | `NSWorkspace.frontmostApplication.bundleIdentifier` at change time, an approximation (section 6.2) |
| `x11_transfer.rs` INCR, size margins | large selections arrive in chunks | none: `dataForType` returns the whole blob. The `max_item_bytes` cap still applies in `core` |
| ADR 0001 "read every Format at copy time" | Mutter re-serves only one type after the owner exits | the same rule holds for another reason: a pasteboard item "is only valid until the owner of the pasteboard changes" ([NSPasteboardItem](https://developer.apple.com/documentation/appkit/nspasteboarditem)) |
| `x11_paste.rs` `X11Paster` | XTest Ctrl+V, Ctrl+Shift+V for terminals by `WM_CLASS` | `CGEvent` Cmd+V posted to the session tap. Terminals on macOS paste with Cmd+V too, so there is no chord table **(inference)**. Needs Accessibility (section 4) |
| `x11_paste.rs` `X11Focus` | `_NET_ACTIVE_WINDOW` with a pager source indication | `NSRunningApplication` of the previous frontmost app, re-activated cooperatively (section 5) |
| `popup.rs` `cursor_position` | X11 pointer query, `None` elsewhere | Tauri's own `AppHandle::cursor_position()` works on macOS (`tauri-2.12.4/src/app.rs:928`), so no platform code is needed |
| `popup.rs` `x11_window` / `take_focus` | ask the WM for focus with retries (Mutter focus-stealing prevention) | `NSApplication.activate()` (macOS 14+), with `ActivationPolicy::Accessory` (section 5) |
| `shortcut.rs` `kind_for_os` | macOS returns `RegistrarKind::None` until "Plan 3" (Ctrl+Cmd+V) | the existing `X11Registrar` (a misnomer: it is the tauri-plugin-global-shortcut registrar) works as is (section 8) |
| `gnome_keys.rs`, Force Super+V, Reset to default | GNOME owns Super+V | not applicable: macOS has no system binding on Ctrl+Cmd+V that we know of **(unverified)**. Force Super+V stays GNOME/Windows only |
| `autostart.rs` | `.desktop` entry with `--autostart` | the plugin's LaunchAgent (default) also passes `--autostart` (section 9) |
| `updater.rs` `METHOD` | in-place install | already `ReleasePage` on macOS; can become in-place once builds are Developer-ID signed (section 7) |
| `tray.rs` "Use Super+V…" | GNOME only (`offers_use_super_v`) | already hidden on macOS (`kind != Gnome`); use a template icon for the menu bar (section 8) |
| `Capabilities` | `source_app`, `auto_paste`, `files`, `backend_name` | `auto_paste` becomes "Accessibility granted", which can change at runtime (section 4) |
| CI (`ci.yml`) | Linux tests under `xvfb-run` | `cargo test` already runs on `macos-latest`; macOS Backend tests can use a private named pasteboard (section 10) |

`store/` already uses `keyring` with `apple-native` on macOS (`Cargo.toml`), so the history key goes to the Keychain with no new work.

## 2. Watching and reading the pasteboard

### 2.1 Polling `changeCount`

- There is no change notification. "The change count subsequently increments each time the pasteboard ownership changes" ([changeCount](https://developer.apple.com/documentation/appkit/nspasteboard/changecount)). R 1.3 already notes that Maccy and Clipy poll every 500 ms.
- **Interval:** Apple gives no recommended interval and says nothing about what one `changeCount` read costs **(unverified)**. Maccy's default is 0.5 s (R 1.3). Start at 500 ms, configurable later **(inference)**.
- **Thread:** in `objc2-app-kit 0.3.2`, `NSPasteboard` is not marked main-thread-only, but it is also not `Send`, so get `NSPasteboard::generalPasteboard()` on the watcher thread itself and keep it there. Apple doesn't document whether `NSPasteboard` is thread-safe **(unverified)**; Maccy polls from a main-thread `Timer`. If background polling misbehaves, fall back to a main-thread timer through `run_on_main_thread` **(inference)**.
- **Startup:** read the current contents once at start, as ADR 0001 asks for Linux. Seed the last-seen `changeCount` *after* that read.

### 2.2 Types to read and how they map to our Formats

UTI strings are from Apple's `UTType` docs:

| Our Format (MIME) | Pasteboard type | Source |
|---|---|---|
| `text/plain;charset=utf-8` | `public.utf8-plain-text` (`NSPasteboard.PasteboardType.string`) | [UTType.utf8PlainText](https://developer.apple.com/documentation/uniformtypeidentifiers/uttype-swift.struct/utf8plaintext) |
| `text/html` | `public.html` | [UTType.html](https://developer.apple.com/documentation/uniformtypeidentifiers/uttype-swift.struct/html) |
| `image/png` | `public.png`; if only `public.tiff` exists, convert TIFF to PNG | [png](https://developer.apple.com/documentation/uniformtypeidentifiers/uttype-swift.struct/png), [tiff](https://developer.apple.com/documentation/uniformtypeidentifiers/uttype-swift.struct/tiff) |
| `text/uri-list` | `public.file-url`, one per pasteboard item; join them as a URI list | [fileURL](https://developer.apple.com/documentation/uniformtypeidentifiers/uttype-swift.struct/fileurl), [pasteboardItems](https://developer.apple.com/documentation/appkit/nspasteboard/pasteboarditems) |
| (not stored today) | `public.rtf` | [rtf](https://developer.apple.com/documentation/uniformtypeidentifiers/uttype-swift.struct/rtf) |

- **Multiple items:** "A pasteboard can contain multiple items" ([NSPasteboard](https://developer.apple.com/documentation/appkit/nspasteboard)). Maccy merges all items into one record because some apps (BBEdit, Edge) put two items on the pasteboard for one copy ([Clipboard.swift](https://github.com/p0deje/Maccy/blob/master/Maccy/Clipboard.swift)). Do the same: one ClipEvent per `changeCount` change.
- **`types` is the union over all items**, "listed in the order they were declared" ([types](https://developer.apple.com/documentation/appkit/nspasteboard/types)), so it is the right place to look for marker types (section 6).
- **TIFF to PNG** needs either the `image` crate's `tiff` feature (a feature change, so it needs the plan to name it) or AppKit's `NSBitmapImageRep` **(inference)**. Which apps put only TIFF on the pasteboard today is **(unverified)**.
- **Names in Rust:** the `NSPasteboardType*` constants are `extern static`s in `objc2-app-kit`, and reading one is `unsafe`. Build the type from its UTI string instead (`NSString::from_str("public.html")`), which is safe **(inference from the binding source)**.

### 2.3 Safe Rust surface (`unsafe_code = "forbid"`)

In `objc2-app-kit 0.3.2` these are plain `pub fn` (safe): `NSPasteboard::generalPasteboard`, `pasteboardWithName`, `pasteboardWithUniqueName`, `changeCount`, `accessBehavior`, `clearContents`, `writeObjects`, `pasteboardItems`, `types`, `dataForType`, `stringForType`, `setData_forType`, `setString_forType`, `detectPatternsForPatterns_completionHandler`, `detectMetadataForTypes_completionHandler`; `NSPasteboardItem::types` / `dataForType`; `NSWorkspace::frontmostApplication`; `NSRunningApplication::bundleIdentifier` / `processIdentifier` / `activateWithOptions` / `activateFromApplication_options`; `NSApplication::setActivationPolicy`. `NSData::with_bytes` / `to_vec` are safe in `objc2-foundation`. In `objc2-core-graphics 0.3.2`, `CGEvent::new_keyboard_event`, `CGEvent::set_flags`, `CGEvent::post`, `CGPreflightPostEventAccess` and `CGRequestPostEventAccess` are safe. The ones that are `unsafe` (`declareTypes_owner`, `readObjectsForClasses_options`, `setPropertyList_forType`) are not needed.

So the Backend can be written without `unsafe`, keeping the crate-wide `forbid` **(inference from the binding source; check it when the code compiles)**. These crates are already transitive dependencies (through `tao`/`tray-icon`), but a direct dependency, and the Cargo features it needs (`NSPasteboard`, `NSPasteboardItem`, `NSWorkspace`, `NSRunningApplication`, `CGEvent`, `CGEventTypes`, `CGRemoteOperation`…), have to be named in the plan (CLAUDE.md "Dependencies"). `AXIsProcessTrustedWithOptions` lives in `objc2-application-services`, which is *not* in the tree; `CGPreflightPostEventAccess` covers the same need (section 4), so it can be avoided.

### 2.4 Echo: our own writes

- `clearContents()` returns "The change count of the receiver", and Apple suggests recording `changeCount` "at the time that you take ownership of the pasteboard and compare it with a later value to determine whether you still have ownership" ([clearContents](https://developer.apple.com/documentation/appkit/nspasteboard/clearcontents()), [changeCount](https://developer.apple.com/documentation/appkit/nspasteboard/changecount)).
- So `write()` does `n = clearContents()`, then writes every Format, and stores `n` as "our count". When the watcher sees `changeCount == our count`, it emits no ClipEvent. That matches X11, which skips its own ownership (`x11.rs:248`) and leaves `prepare_paste` to bump the Clip. `core::rules::echo_target` stays as the hash-based safety net and needs no change.
- Race: if another app copies between our `clearContents` and the next poll, `changeCount` moves past our count and the change is read normally. That is correct, since ownership changed **(inference)**.
- Run `write()` on the watcher thread (command channel, like `x11.rs`) or guard "our count" with a mutex. The poll must not read between `clearContents` and the last `setData` **(inference)**.

## 3. Pasteboard privacy: status on 2026-11-23

What Apple documents (all macOS 15.4+):

- `.default`: "The default behavior for the General pasteboard is to ask upon programmatic access. **All other pasteboards default to always allow access.** … Once programmatic pasteboard access triggers the first pasteboard access alert, the state automatically changes to `.ask`. At this point the app starts being shown in System Settings, where the user can toggle the behavior between `.ask`, `.alwaysAllow`, and `.alwaysDeny`." ([default](https://developer.apple.com/documentation/appkit/nspasteboard/accessbehavior-swift.enum/default))
- `.ask` and `.alwaysDeny` both still allow "access that is both user originated and paste related" ([ask](https://developer.apple.com/documentation/appkit/nspasteboard/accessbehavior-swift.enum/ask), [alwaysDeny](https://developer.apple.com/documentation/appkit/nspasteboard/accessbehavior-swift.enum/alwaysdeny)). A background watcher read is neither, so under `.alwaysDeny` the Backend sees nothing, and under `.ask` the user is prompted **(inference)**.
- `accessBehavior` is read-only and reflects the user's choice ([accessBehavior](https://developer.apple.com/documentation/appkit/nspasteboard/accessbehavior-86972)).
- `detectPatterns(for:)` "doesn't allow the app to access the item's contents. As a result, the system doesn't notify the person" ([detectPatterns](https://developer.apple.com/documentation/appkit/nspasteboard/detectpatterns(for:))).

What changed since R: nothing new from Apple. I checked the macOS 26, 26.1–26.6, 27, 27.2 and 27.3 (beta 2) release notes ([index](https://developer.apple.com/documentation/macos-release-notes)). The only pasteboard entry is still 27.2's "The `EnablePasteboardPrivacyDeveloperPreview` user default has been removed" ([27.2 notes](https://developer.apple.com/documentation/macos-release-notes/macos-27_2-release-notes)). No note says enforcement is now on, or that it was dropped.

- **Is the alert enforced by default on macOS 26/27? (unverified).** Secondary sources disagree. Michael Tsai's blog reports a Settings section "Paste from Other Apps" and a clipboard app (ClipBar) that prompted on every change until the user chose Allow ([mjtsai.com](https://mjtsai.com/blog/2025/05/12/pasteboard-privacy-preview-in-macos-15-4/)); that is not a primary source. **Test it on a real macOS 27 machine before committing to a UX.**
- **Do `changeCount` and `types` count as "programmatic access"? (unverified).** Apple only says what the detect methods avoid. Maccy reads `types` before contents.

**Design consequence (inference):** treat this like Accessibility.
- On start, read `accessBehavior`. If it is `.alwaysDeny`, report it in `StartupReport` and the tray tooltip ("Clipboard access denied in System Settings → Privacy & Security").
- If it is `.default`/`.ask`, show a first-run explanation *before* the first read, so the system alert is not a surprise.
- Never retry in a loop under `.ask`: one alert per change would be hostile (the ClipBar report above).
- Add the access state to `Capabilities` (or `StartupReport`) so the UI can grey out with a reason, as GLOSSARY "Capabilities" intends.

## 4. Auto-paste: Accessibility, and the macOS 27.3 change

### 4.1 Mechanism

- Post Cmd+V with `CGEvent(keyboardEventSource:virtualKey:keyDown:)`, set the Command flag, and `post(tap: .cgSessionEventTap)`, as Maccy does ([Clipboard.swift](https://github.com/p0deje/Maccy/blob/master/Maccy/Clipboard.swift)). `CGEventPost` "posts the specified event immediately before any event taps instantiated for that location" ([post(tap:)](https://developer.apple.com/documentation/coregraphics/cgevent/post(tap:))).
- Key code: V is virtual key `0x09` (`kVK_ANSI_V`, Carbon `Events.h`), a physical key position, not a character. Maccy has extra handling for layouts where Command switches to QWERTY (`commandSwitchesToQWERTY`) ([Clipboard.swift](https://github.com/p0deje/Maccy/blob/master/Maccy/Clipboard.swift)), so non-US layouts need a test **(unverified which layouts break)**.
- **Permission check:** `CGPreflightPostEventAccess()` / `CGRequestPostEventAccess()` (macOS 10.15+; [preflight](https://developer.apple.com/documentation/coregraphics/cgpreflightposteventaccess()), [request](https://developer.apple.com/documentation/coregraphics/cgrequestposteventaccess())), or `AXIsProcessTrustedWithOptions` with `kAXTrustedCheckOptionPrompt`, where "Prompting occurs asynchronously and does not affect the return value" ([AXIsProcessTrustedWithOptions](https://developer.apple.com/documentation/applicationservices/1459186-axisprocesstrustedwithoptions)). Apple's pages for the two CG functions have no description text; that they map to the same Accessibility grant is **(unverified)** (R section 2 says the same).
- `Capabilities.auto_paste` must be computed at runtime. The grant can arrive while the app runs (the user flips the switch), so re-check before each paste, not only at startup **(inference)**.
- Keep the Linux safety rule (platform-clipboard skill): never post keys unless the frontmost app is the recorded target. Compare `NSWorkspace.frontmostApplication.processIdentifier` with the target pid right before posting.

### 4.2 macOS 27.3 beta 2 (new since R; dated 2026-11, beta)

The macOS 27.3 beta 2 release notes, under Privacy & Security ([27.3 notes](https://developer.apple.com/documentation/macos-release-notes/macos-27_3-release-notes)):

- "A split of Device Control and Data Access into two settings: (1) System & App Protection Override, and (2) Accessibility", plus "The option for users to configure apps to ask every time they require access" and "A transparency indicator when a requesting app is controlling another app using System & App Protection Override".
- "Users will see these updates when approving new app permission requests. All app permissions previously granted by users will remain in effect."
- "If your apps use … the new Accessibility settings to provide assistive technologies, you can request entitlements to deliver the same experience for new installations that they offered before macOS 27.3. Currently, known apps aren't affected … Additional entitlement details will be available soon. (192585326)"
- Known issue: "Apps that use the CoreGraphics API to post input events, such as mouse and keyboard events, might not display a live activity properly. This issue does not affect apps that use the Accessibility API or apps that install listening event taps. (192728601)"

What this means for us:
- Posting `CGEvent` keystrokes is explicitly in scope (the live-activity known issue names it). Apparently there is now an on-screen indicator while an app posts input events **(inference)**.
- Which of the two new panes `CGEventPost` falls under, whether a non-assistive app like a clipboard manager can get the entitlement, and whether "ask every time" would apply per paste: all **(unverified)**. Apple says details are coming.
- **Recommendation:** design auto-paste as optional from day one, as it already is on XWayland (`Capabilities.auto_paste = false`, Clip copied, user presses Cmd+V). Do not make the macOS release depend on it. Re-check the 27.3 final release notes before implementing section 4.

### 4.3 Sandbox

R already covers it: Maccy ships sandboxed and still pastes. For a Developer-ID (non-App-Store) build, use **no App Sandbox**. Nothing we need requires it, and `string`-typed file paths are off-limits to sandboxed apps ([PasteboardType.string](https://developer.apple.com/documentation/appkit/nspasteboard/pasteboardtype/string)). Whether App Review would accept the app is out of scope here (R open question 4).

## 5. Popup focus and returning to the previous app

- **Tauri has no NSPanel.** tao's window class is `TaoWindow`, declared with `class!(NSWindow)` as superclass (`tao-0.37.1/src/platform_impl/macos/window.rs:407`). `nonactivatingPanel` means "The window is a panel or a subclass of NSPanel that does not activate the owning app" ([nonactivatingPanel](https://developer.apple.com/documentation/appkit/nswindow/stylemask-swift.struct/nonactivatingpanel)), so it can't be set on a Tauri window. Maccy uses an `NSPanel` subclass with `.nonactivatingPanel`, `level = .statusBar` and `.fullScreenAuxiliary` ([FloatingPanel.swift](https://github.com/p0deje/Maccy/blob/master/Maccy/FloatingPanel.swift)). Getting that in Tauri needs a third-party plugin or our own runtime class swizzling (`unsafe`). The forbid lint rules out the second; the first is a new dependency.
- **Recommended path (no new deps):** use the activating model the existing traits already describe.
  1. In `setup`, `app.set_activation_policy(ActivationPolicy::Accessory)` (`tauri-2.12.4/src/app.rs:658`). Accessory means "doesn't appear in the Dock and doesn't have a menu bar, but it may be activated programmatically or by clicking on one of its windows" ([accessory](https://developer.apple.com/documentation/appkit/nsapplication/activationpolicy-swift.enum/accessory)). Alternatively set `LSUIElement` in an `Info.plist` merged through `bundle.macOS.infoPlist` ([Tauri config](https://v2.tauri.app/reference/config/)), which Maccy does ([Info.plist](https://github.com/p0deje/Maccy/blob/master/Maccy/Info.plist)).
  2. `FocusTracker::current()` returns the frontmost app's pid in `FocusedWindow(u64)`. `frontmostApplication` is "the app that receives key events" ([frontmostApplication](https://developer.apple.com/documentation/appkit/nsworkspace/frontmostapplication)). Read it *before* the popup shows, as `popup::toggle_now` already does.
  3. Show the popup and activate ourselves (`win.set_focus()`, or `NSApplication.activate()`, macOS 14+: "calling this method doesn't guarantee app activation" ([activate()](https://developer.apple.com/documentation/appkit/nsapplication/activate()))). The X11 retry loop in `popup::activate` is probably unnecessary here **(inference)**.
  4. `FocusTracker::restore(target)`: hide the popup, `NSApp.yieldActivation(to: target)`, then `target.activate(from: current, options: [])`. Apple's model is cooperative: "the other application should call yieldActivation(to:) or equivalent prior to the target application invoking activate()" ([activate(from:options:)](https://developer.apple.com/documentation/appkit/nsrunningapplication/activate(from:options:)), [yieldActivation(to:)](https://developer.apple.com/documentation/appkit/nsapplication/yieldactivation(to:))). All of these are safe in `objc2-app-kit 0.3.2`: `NSApplication::activate`, `yieldActivationToApplication` (`NSApplication.rs:571,582`) and `NSRunningApplication::activateFromApplication_options`. `activateIgnoringOtherApps` is discouraged ("You should rarely pass this flag") ([docs](https://developer.apple.com/documentation/appkit/nsapplication/activationoptions/activateignoringotherapps)).
  5. Poll `frontmostApplication` until it is the target (as `X11Focus` waits up to 300 ms), then paste.
- **Full-screen apps and Spaces:** tao windows can be made visible on all workspaces (`visibleOnAllWorkspaces`), but whether a Tauri window shows over another app's full-screen Space without `.fullScreenAuxiliary` is **(unverified)**. Put it on the manual checklist.
- **`transparent: true`** in `tauri.conf.json`: `app.macOSPrivateApi` "Enables the transparent background API" and is "a no-op in Tauri 2.12.1+, because the APIs are always enabled now" ([Tauri config](https://v2.tauri.app/reference/config/)). This repo locks `tauri 2.12.4`, so no change is needed.

## 6. Requirement: honor the clipboard secret-marker conventions

This is a **firm requirement** for the macOS Backend, decided by the maintainer. It is the macOS equivalent of `x-kde-passwordManagerHint` on Linux (`src-tauri/src/platform/linux/x11.rs:310`).

### 6.1 Reading: skip marked content

The Backend **must** check `NSPasteboard.types` (the union over all items, [types](https://developer.apple.com/documentation/appkit/nspasteboard/types)) **before reading any data**. If any marker below is present, it emits `ClipEvent { formats: vec![], source_app: None, secret: true }` and reads nothing else, exactly like the X11 path.

Markers defined by [nspasteboard.org](http://nspasteboard.org/):

| Type | nspasteboard.org says | Our action |
|---|---|---|
| `org.nspasteboard.ConcealedType` | confidential; "If displayed on screen it should be visually obfuscated", "Avoid recording it to a file, or consider encrypting it" | skip: `secret: true` |
| `org.nspasteboard.TransientType` | "Data marked transient should not be recorded or displayed in a pasteboard history" | skip: `secret: true` |
| `org.nspasteboard.AutoGeneratedType` | content the user did not intend to copy; "probably should not be recorded as part of the pasteboard history" | skip: `secret: true` |

Legacy and proprietary markers that nspasteboard.org lists and asks history apps to support ("Add support for existing proprietary identifiers… not already supported by your application"):

| Type | Meaning per nspasteboard.org | Our action |
|---|---|---|
| `com.agilebits.onepassword` | confidential (1Password) | skip: `secret: true` |
| `de.petermaurer.TransientPasteboardType` | transient | skip: `secret: true` |
| `com.typeit4me.clipping` | transient | skip: `secret: true` |
| `Pasteboard generator type` | transient | skip: `secret: true` |
| `com.apple.is-remote-clipboard` | copied from another device (Universal Clipboard), added to the page 2025-04-17 | **not** a secret marker. Record normally (a later setting could skip it) **(inference)** |

How it maps onto `core/`:
- No new decision code is needed. `core::rules::decide` already returns `Skip(SkipReason::Secret)` when `event.secret` is true, before the excluded-app, empty and size checks. Keep the marker list as a pure function in `core/` with a unit test per marker, the way `x11.rs` has `password_hint_sets_secret_flag`. For example: `core::rules::is_secret_marker(&[&str]) -> bool` over the type strings. The Backend then only does I/O, as CLAUDE.md asks.
- The Linux check would ideally move into the same pure function later. It is a value check (`== "secret"`), not a presence check, so it needs its own branch.
- Because `secret: true` events carry no Formats, nothing confidential reaches the store or the Echo hash. Under pasteboard privacy (section 3), checking `types` first also means no content is read for marked items **(inference; whether reading `types` itself can trigger the alert is unverified)**.
- The macOS Backend's `formats` read must ignore the marker types themselves (they are not Formats).

### 6.2 Fallback: excluded apps by bundle identifier

No OS enforces these markers; an app that doesn't set them is recorded. The backstop is `Settings.excluded_apps`, which `decide` matches case-insensitively against `ClipEvent.source_app` (`core/rules.rs:82`).

- On macOS, `source_app` is the bundle identifier of `NSWorkspace.shared.frontmostApplication`, "the app that receives key events" ([frontmostApplication](https://developer.apple.com/documentation/appkit/nsworkspace/frontmostapplication)), read in the same poll that saw the change. `bundleIdentifier` is safe in objc2 (section 2.3).
- This is an approximation. nspasteboard.org warns that apps polling `changeCount` "would likely assume" the focused app is the source. A copy made by a background app is attributed to whatever app is in front. When an item carries `org.nspasteboard.source`, prefer its value ("the bundle identifier of the source app"; for display "for informational purposes only", and it may be the empty string) ([nspasteboard.org](http://nspasteboard.org/)). Maccy uses `frontmostApplication` the same way ([Clipboard.swift](https://github.com/p0deje/Maccy/blob/master/Maccy/Clipboard.swift)).
- The 500 ms poll gap makes the approximation worse: the user may switch apps between the copy and the poll **(inference)**.
- `Capabilities.source_app = true` on macOS.
- **Default bundle IDs for password managers: (unverified).** I found no primary source (vendor docs) giving them. Candidates commonly seen are `com.1password.1password` (1Password 8), `com.bitwarden.desktop`, `org.keepassxc.keepassxc` and `com.apple.Passwords`. Treat all of them as **unverified**: check each against the installed app's `Info.plist` (`CFBundleIdentifier`) before shipping them as defaults. 1Password marks its copies (`com.agilebits.onepassword` per nspasteboard.org); whether current versions also set `ConcealedType` is **(unverified)**.
- Settings note: on Linux the same list holds process names (`/proc/<pid>/comm`, e.g. the test value `keepassxc`). A settings file is per machine, so the mixed meaning is harmless, but the settings UI should label the field per OS **(inference)**.

### 6.3 Writing: mark our own writes

When the app writes a Clip back (`ClipboardBackend::write`), it **must** add `org.nspasteboard.TransientType` (empty data) to the item, so other history tools don't record our paste again as a new entry. nspasteboard.org: transient data "should not be recorded or displayed in a pasteboard history". Add `org.nspasteboard.source` too, with the Clip's original source bundle id, or the empty string when unknown, which nspasteboard.org explicitly allows ([nspasteboard.org](http://nspasteboard.org/)).

How this fits with Echo detection:
- The watcher must recognise its own write **by `changeCount`, before** the marker check (section 2.4: record the value `clearContents()` returns). If it only checked markers, our write would arrive as `secret: true` and be dropped, which is harmless today because `prepare_paste` already bumped the Clip, but it would leave `Engine.own_write` to be consumed by the next unrelated event. Skipping by `changeCount` keeps macOS identical to X11 (`x11.rs:248`).
- If another app's copy overwrites ours before the next poll, `changeCount` differs and that copy is read normally. Our marker is gone with our item.
- Trade-off: other clipboard managers will not show our paste as the current item either ("not be recorded *or displayed*"). Maccy instead writes its own `org.p0deje.Maccy` type plus `org.nspasteboard.source` and no Transient marker ([Clipboard.swift](https://github.com/p0deje/Maccy/blob/master/Maccy/Clipboard.swift)). The maintainer chose TransientType; this note records the consequence only.
- Never write `ConcealedType` for a normal Clip. Clips that were concealed are never stored, so they can never be written back.

## 7. Signing, notarization, updates

R section 6 covers the requirements (Developer ID, notarization since 10.15, App Store rules). New here:

- **Cost:** "The Apple Developer Program is 99 USD per membership year" ([Apple](https://developer.apple.com/programs/whats-included/)). Tauri: "Only the Apple Developer `Account Holder` can create _Developer ID Application_ certificates", "Notarization is required when using a _Developer ID Application_ certificate", and with a free account "you will not be able to notarize your application" ([Tauri macOS signing](https://v2.tauri.app/distribute/sign/macos/)).
- **CI secrets for `tauri-action`:** `APPLE_CERTIFICATE` (base64 `.p12`), `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY`, plus either `APPLE_ID`/`APPLE_PASSWORD` (app-specific)/`APPLE_TEAM_ID` or `APPLE_API_ISSUER`/`APPLE_API_KEY`/`APPLE_API_KEY_PATH` ([Tauri](https://v2.tauri.app/distribute/sign/macos/)). `release.yml` sets none of these today, so the macOS DMGs it publishes are unsigned.
- **Hardened runtime** is on by default (`bundle.macOS.hardenedRuntime`, default `true`), and entitlements come from `bundle.macOS.entitlements` ([Tauri config](https://v2.tauri.app/reference/config/)). Posting CGEvents and reading the pasteboard need no entitlement that I could find **(unverified)**. The 27.3 Accessibility entitlement is still to be detailed (section 4.2). Whether WKWebView under hardened runtime needs `com.apple.security.cs.allow-jit` for Tauri apps is **(unverified)**; Tauri's signing page doesn't mention entitlements.
- **Gatekeeper:** "In macOS Sequoia, users will no longer be able to Control-click to override Gatekeeper when opening software that isn't signed correctly or notarized. They'll need to visit System Settings > Privacy & Security" ([Apple news, 2024-08-06](https://developer.apple.com/news/?id=saqachfa)). Ad-hoc signing (`signingIdentity: "-"`) "does not prevent MacOS from requiring users to" approve the app there ([Tauri](https://v2.tauri.app/distribute/sign/macos/)).
- **TCC grants survive updates only with a stable signature.** Apple DTS: "Ad hoc signed code does not include a stable DR, and thus macOS is unable to tell that version N+1 of your app is the 'same code' as version N" ([forum thread 795739](https://developer.apple.com/forums/thread/795739); background: [TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements)). An unsigned or ad-hoc build would lose Accessibility, and probably the pasteboard "Always Allow" choice **(inference)**, on every update. **That makes Developer ID signing effectively mandatory for a usable macOS release.**
- **Updater:** `updater.rs` uses `UpdateMethod::ReleasePage` on macOS, and `RELEASING.md` says silent updates there need a Developer ID certificate. Once signing is in place, `METHOD` can become `InPlace` on macOS too (the plugin has macOS-specific install code, `tauri-plugin-updater-2.14.1/src/updater.rs`) **(inference)**. The download-count workflow's exclusion of `*.app.tar.gz` would then undercount macOS updates, which is fine.
- `bundle.macOS.minimumSystemVersion` defaults to `"10.13"` ([Tauri config](https://v2.tauri.app/reference/config/)). `activate()`/`yieldActivation` need 14.0 and `accessBehavior` needs 15.4 (Apple pages above). Set the minimum to 14.0, or gate the calls at runtime **(inference)**.

## 8. Global shortcut, tray, Dock

- **Shortcut:** `tauri-plugin-global-shortcut 2.4.1` uses `global-hotkey 0.8`, which registers with Carbon `RegisterEventHotKey` on macOS (`global-hotkey` [macos/mod.rs](https://github.com/tauri-apps/global-hotkey/blob/dev/src/platform_impl/macos/mod.rs)). An event tap is used only for media keys, which we don't register.
  - Apple, on macOS 15: "macOS Sequoia now requires that a hotkey registration use at least one modifier that is not shift or option". This was later "addressed in macOS 15.2 Beta 2… The hotkey API now allows hotkeys with only Option (or Option-Shift)" (Apple Frameworks Engineer, [forum thread 763878](https://developer.apple.com/forums/thread/763878), Sep and Nov 2024). The planned **Ctrl+Cmd+V** is unaffected either way.
  - No TCC prompt is documented for `RegisterEventHotKey` **(unverified; R open item)**.
  - Change `kind_for_os` to return `Plugin` on macOS, with `DEFAULT_SHORTCUT` per OS. Cmd+V must never be registered (`shortcut.rs` comment).
- **Tray:** Tauri's tray works in the macOS menu bar. Use `TrayIconBuilder::icon_as_template(true)` ("Use the icon as a template… macOS only", `tauri-2.12.4/src/tray/mod.rs:294`) so it adapts to light/dark menu bars. That needs a monochrome template icon asset.
- **Dock:** `ActivationPolicy::Accessory` or `set_dock_visibility(false)` (`tauri-2.12.4/src/app.rs:658,678`). The settings window can still be shown; an Accessory app has no menu bar of its own, so Cmd+Q / Edit-menu shortcuts in the settings window need checking **(unverified)**.

## 9. Autostart

- `tauri-plugin-autostart 2.7.0` exposes only `MacosLauncher::LaunchAgent` (default) and `AppleScript` (`src/lib.rs:28`). It sits on `auto-launch 0.6.0`, which *also* has `MacOSLaunchMode::SMAppService` ("macOS 13+", `auto-launch-0.6.0/src/lib.rs:330`), but the plugin doesn't expose it.
- The LaunchAgent plist written by `auto-launch` has `ProgramArguments` (so `--autostart` is passed, as `core::launch` expects), `RunAtLoad`, and `AssociatedBundleIdentifiers` (`auto-launch-0.6.0/src/macos.rs:270-310`). That is enough for the current code to work unchanged **(inference)**.
- Apple's direction is `SMAppService`: "In macOS 13 and later, use SMAppService to register and control LoginItems, LaunchAgents, and LaunchDaemons… the register() and unregister() methods provide a replacement for installing property lists in ~/Library/LaunchAgents" ([SMAppService](https://developer.apple.com/documentation/servicemanagement/smappservice)). `SMAppService.mainApp` launches the main app at login ([mainApp](https://developer.apple.com/documentation/servicemanagement/smappservice/mainapp)) but documents no way to pass arguments, so `--autostart` detection would need another signal **(inference)**.
- The `AppleScript` mode talks to System Events, which likely triggers an Automation (Apple Events) TCC prompt **(unverified)**. Keep the LaunchAgent default.
- Whether macOS 13+ shows a "background item added" notification for a plain plist LaunchAgent is **(unverified)**. Check it on the manual checklist.

## 10. CI and testing

- `ci.yml` already runs `cargo check` and `cargo test --locked` on `macos-latest`, so a `#[cfg(target_os = "macos")]` Backend is compiled and unit-tested on every push with no workflow change.

Also Backend read/write round-trips **against a private pasteboard**. Make the Backend take its pasteboard as a constructor parameter, and have tests use `NSPasteboard::pasteboardWithUniqueName()` (safe in objc2). Apple: "All other pasteboards [than General] default to always allow access" ([default](https://developer.apple.com/documentation/appkit/nspasteboard/accessbehavior-swift.enum/default)), so tests never trigger the privacy alert. That this works on GitHub's macOS runners (which need a pasteboard server in the session) is **(unverified)**. If it fails there, mark those tests `#[ignore = "display"]`.

## 12. Risks and unknowns

1. **macOS 27.3 Accessibility split** (section 4.2). It could make auto-paste need an entitlement we can't get, or a per-use prompt. Mitigation: auto-paste stays optional; copy-only is the baseline.
2. **Pasteboard privacy enforcement** (section 3). If the alert is live, the first-run flow must lead the user to "Always Allow", and `.alwaysDeny` must be reported clearly. Not testable without a real Mac on 27.x.
3. **Signing cost and pipeline.** Without Developer ID every update resets TCC grants, which ruins both permissions. That is $99/yr plus CI secrets.
4. **Focus handoff** with the activating popup: race between hiding the popup, re-activating the target and posting Cmd+V. Behaviour with full-screen apps and Spaces is untested.
5. **Source-app attribution** is approximate (frontmost app at poll time). Excluded-app rules are only as good as that.
6. **Main-thread rules** for `NSPasteboard` / `NSWorkspace` from a background thread are undocumented. There may be a fallback to a main-thread timer.
7. **Keyboard layouts** for virtual key `0x09` (Dvorak-QWERTY⌘ and similar).
8. **Bundle IDs** for default exclusions are unverified (section 6.2).

## 13. Suggested implementation order

1. **Pure core pieces with tests:** the secret-marker predicate, UTI↔MIME mapping, file-URL list joining, the own-write `changeCount` decision, and `kind_for_os` → `Plugin` with a macOS default shortcut. They compile and run on every CI OS.
2. **`platform/macos/` Backend, watch + read + write**, constructed with an injectable pasteboard. Round-trip tests on a unique named pasteboard. Wire `make_backend` under `#[cfg(target_os = "macos")]`. Read once at startup.
3. **Secret markers and Transient-on-write** (section 6), with tests on the private pasteboard (write a `ConcealedType` item and assert one `secret: true` ClipEvent with no Formats).
4. **Source app + excluded apps** via `frontmostApplication` / `org.nspasteboard.source`.
5. **App shell:** `ActivationPolicy::Accessory`, template tray icon, global shortcut (Ctrl+Cmd+V), popup placement via Tauri's `cursor_position`. At this point the app is usable copy-only on macOS.
6. **Pasteboard privacy UX:** `accessBehavior` in `StartupReport`/Capabilities, first-run explanation.
7. **Signing + notarization** in `release.yml` (Developer ID secrets), then switch `updater.rs` to `InPlace` on macOS.
8. **Auto-paste last:** `MacFocus` (pid, yield + activate, wait for frontmost) and `MacPaster` (CGEvent Cmd+V, frontmost check right before posting), gated by `CGPreflightPostEventAccess`. Only after re-reading the final macOS 27.3 notes.
9. **Manual checklist:** add a macOS section to the `desktop-test` skill (privacy alert, Accessibility grant surviving an update, full-screen Spaces, non-US layouts, LaunchAgent at login).
